Blackbox: every failure on the BEAM, and what came before it

The ask: "the most useful and amazing error/exception/bug tracking observability tool for elixir there ever could be. it should get ALL errors that occur in the beam ... especially what happened before any given error ... prove TDD everything technical that is not clear." Eight agents read sentry-elixir and every other BEAM tool, counted what developers say, and ran five labs of 256 tests against Elixir 1.20.4 and OTP 28. A ninth agent then attacked the draft: it reran every suite, added 17 tests and 12 mutation checks, and found three blockers. This page is the revised result.

Blackbox, a flight recorder for the BEAM

Blackbox (blackbox) is a library, kept in packages/blackbox/ for now and planned as a hex package. It catches every failure the BEAM lets it see, keeps what happened before each one, stores it in the app's own Postgres and shows one timeline per failure to people and to agents. 1charta is its first user. v1 is the spike, ported and hardened, not a rewrite; what the review found unproven or unneeded for 1charta waits (ADR section 11). The decision in eight lines:

One install, its own OTP app:blackbox boots before the host and stops after it. A primary filter of its own catches the SASL reports Elixir hides, with no setting changed; one :logger handler at :all splits events from crumbs; telemetry for Phoenix, Plug and Bandit. A watchdog re-adds what gets removed.
One failure, one occurrenceA 500 is sighted four times in one process. A process-dictionary mark remembers which sources saw it: a new source merges, a source seen before is a real repeat and counts.
A ring in every busy process50 crumbs in the process dictionary, 42 ns each, binaries capped at 200 B, Logger text scrubbed when added, reset per request. The handler runs in the dying process, so it reads the ring for free.
Cause across processesOwn ring, then $callers to a live parent (Tasks), then client_info (GenServer calls). Casts and sends wait for the seq_trace label, which is later.
Locals, the BEAM wayThe last message, the state, the :sys log and the caller's stack are already in OTP's crash report. Nobody else reads them. Blackbox does, through format_status/1 and the scrubber.
Never hurts the appIn the failing process: classify, fingerprint, send raw bounded terms. An atomics cap, an aggregating buffer, one writer on its own one-connection pool, a flush on stop and a spool file.
Its own Postgres, no servicesTwo tables, upsert by fingerprint, 100 occurrences per issue, 30 days. Open, resolved, muted; "regressed" is derived. No Kafka, no SaaS, no network on the error path.
Agents read, never runJSON and Markdown routes behind a required authorize; event text in a fence longer than any backtick run; browser events marked untrusted. PhantomFix (VU#212479) is why.

Ten beliefs the BEAM corrected

Each card: what the agent wrote down first, what the test showed instead, and the test ids. Red tags went red on their first run; grey tags are supporting tests that were green. Many of the ADR's decisions exist because one of these went red.

A GenServer that raises in init reaches a handler at :all.

Nothing reaches any handler. Elixir's primary logger_translator filter runs with sasl: false and stops every [:otp, :sasl] report: init crashes, restarts, give-ups, brutal kills.

06-908-704-1504-27..29
Logger.configure(handle_sasl_reports: true) at runtime turns them on.

It does nothing. What works: a primary filter of our own, added with :logger.add_primary_filter/2. It is prepended, so it runs before the translator, sees the reports and passes the event on untouched.

08-704-7104-77
10,000 crashing spawns at once: the handler sees 10,000.

1,665 to 4,799 arrive. :logger_proxy enters drop mode and the VM discards emulator reports; two :notice lines say so, with no count.

04-68
A throw in handle_info is reported as {:nocatch, :boom}.

In a GenServer callback a throw is a return value: {:bad_return_value, :boom} with an empty stack.

04-19
A handler that logs from inside log/2 does not recurse.

It recurses with no OTP guard; only the test's own counter cap at 1,000 stopped it. And a handler that raises is removed, announced only at :debug.

04-6404-60
A crash in a call reports {:"$gen_call", from, msg} as the last message.

last_message is the bare request. The caller is in client_info: its pid and its live stacktrace.

06-12
A spawned Task does not inherit the seq_trace label.

Every spawned process inherits it, Task or raw spawn, and the review saw it reach the lib's own writer (10-9a). That is why the label waits for later.

06-2510-9a
put_process_level(:debug) opens debug logs for one process.

Impossible: the process level is a primary filter that can only drop. Per-module levels work, so debug crumbs are opt-in per module.

06-47
Phoenix's router_dispatch exception carries the RuntimeError.

It carries a Plug.Conn.WrapperError, and the conn in the metadata is the one from before the controller. The inner conn is the right one.

05-3
An application that stops is logged at :info; sentry's crash event has the last message and state.

Application exits are :notice, below :error (04-37). Sentry's raise path skips the parsing that would add last message and state (01-2a).

The review: what it broke, and what the ADR does now

After the draft, agent 10 did a heavy-scrutiny review (report 10). It reran every lab one at a time, wrote 17 claim tests of its own in lab/10-review (2 red first), and ran 12 mutation checks: each breaks one claimed behaviour in a copy of the spike and runs the spike's tests. 9 of 12 mutations turned a test red. The three that survived were exactly the grouping and memory claims the ADR leaned on: the anonymous-fun strip (M2), frame selection (M11) and the ring bound (M7). The ADR was revised on every finding.

Three blockers

R-1 · The handler level contradicted the crumbsA :notice handler never receives :info (10-12), so info crumbs through the handler could not work. Now: the handler runs at :all, the primary level decides what arrives, and log/2 splits events from crumbs.
R-2 · 1charta's privacy was not metLast messages carry board ops and chat text positionally ({:apply, ops, ...}, {:say, from, text}); exception messages embed values (Postgrex Key (name)=(my-private-space), KeyError prints the map, 10-11); crumbs held raw /b/<id> lines; /tab/error posts the board key. Now: format_status/1 covers state, message and log; value-bearing exceptions are scrubbed field by field; call messages in exit reasons are reduced to their tag; crumb text is scrubbed when added; capture_browser/2 never gets the key.
R-3 · Boot and shutdown lost the failures that matter mostStarted after the Repo, nothing caught boot crashes; nothing flushed on stop, so a deploy's last batch and a start_permanent halt's cascade died with the VM. Now: capture starts from Blackbox's own OTP application, the store attachment flushes on stop, and what is left goes to a spool file imported on the next boot.

What held up

  • The BEAM facts: the translator hides SASL by default; a prepended primary filter sees it (04-71/72/75/77 green on the rerun); Logger.add_translator/1 keeps it first (10-7); its cost is noise, 0.67 vs 0.64 µs (10-8); a raising filter is removed and logging goes on (10-5).
  • The pipeline: in-flight cap, merge-back, writer kill, self-skip and upsert counts all turn the spike's tests red when broken (M1, M3-M6, M8-M10, M12).
  • The DB-down test is real: 30,000 of 30,000 stored after recovery on the rerun. "0 dropped" is a counted zero checked against Postgres (for one fingerprint).
  • backtrace_depth 32 over 8 costs noise: 47.47 vs 47.58 µs per deep raise (10-16). Report 01 reran 27 of 27.
One caveatOn the review's rerun, 05-43 failed once under full-suite load: the pool closed the socket (DBConnection.ConnectionError{reason: :closed}) before query_canceled arrived. Alone it passed 5 of 5. So "every suite green three runs in a row" does not hold for lab 05 on that run.

One HTTP 500, seen four times, stored once

One raise in a Phoenix controller on Bandit is sighted by three telemetry events and one log line. All four run synchronously in the same Bandit connection process, telemetry first, logger last (05-5, 05-6). So each failure leaves a mark in that process's dictionary, {key, sources} with key = {fingerprint, reason hash}, for 1 s. A sighting from a source the mark has not seen yet is the same failure: it merges its fields and counts nothing. A sighting from a source the mark already has is a new failure and counts. No shared state; the check costs 0.1 µs (05-59, 05-64).

Cowboy, later

Plug.Cowboy runs the plug in a request process, but the [:cowboy, :request, :exception] event and the :error log come from the connection process (05-19, 05-22, red first). The mark is invisible there. Lab 05 proposed a content key, phash2({kind, reason, stack}) in ETS for 1.9 µs (05-60, 05-61), but the review found it would merge equal failures of different requests under a flood (R-6). Cowboy waits for section 11, and its dedupe must pair sightings (count one down per key), not suppress. 1charta runs Bandit.

Two more rules: a supervisor's child_terminated is merged into the child's event when the child reported, and kept as exit :killed when it is the only witness (08-34, 08-35); a give-up is its own issue (08-36). plug_status below 500, :normal, :shutdown and {:shutdown, _} are counters per kind, not issues.

What came before

Every tool in the field keeps "before" as a bounded ring shipped only with an error: Rollbar 100 events, Honeybadger 40, Sentry replay 60 s, Go's FlightRecorder by bytes, JFR under 1 % overhead (report 03). On the BEAM the best place for that ring is the process that does the work.

The crumb ring

Each process that logs or emits a crumb event keeps 50 entries in its own process dictionary as {count, list}, trimmed at 100, µs timestamps. 42 ns per add, freed by the VM with the process (06-6, 06-7). Two shared stores were tried and rejected: one GenServer drowned with 8,560,997 messages queued after 3 s of 8 writers, and an ETS ring held 371,920 rows, 59 MB, of dead pids (06-A).

Small terms only. The review found a 100-byte slice kept a 4 MB binary alive for the life of the process (10-10), so binaries are copied and capped at 200 bytes when added. Logger crumb text is scrubbed when added: the dictionary shows up in Process.info/2, observer and crash reports, so it must never hold a secret. Ceiling: about 15 KB per process that ever logged, cleared per request; a test asserts the ring's :erts_debug.flat_size bound, because the spike's ring passed every test untrimmed (M7).

Default sources, all in the process that does the work: Logger events below :error at the host's level, through the handler (it runs in the caller); telemetry of loaded libs, 125 ns each (Phoenix endpoint and router, Bandit request, Ecto without params, Finch and Req); Blackbox.crumb/3. Debug crumbs are opt-in per module, because lowering the primary level is what costs (06-46) and put_process_level cannot open debug for one process (06-47, red). Turning them on also sets the console handler to the old level, so the console does not start printing them; that is a setting change, and the docs say so (06-2, R-23).

Reset per request

Bandit runs every keep-alive request of a connection in one process (06-42). Without a reset, request N's crumbs show up in request N+1's crash. So the ring is reset on [:bandit, :request, :start] and [:phoenix, :endpoint, :start] (06-43), and a crash then carries exactly its own request's crumbs (06-44).

Joining a failure to its cause, cheapest first

Done inside the handler, before anything leaves the dying process (06-49..51). Each step runs only if the one before found nothing. v1 has three steps; the other two wait.

When the label comes back (section 11) it will be the request's pid, so a live request needs no table, and the handler clears its token around its own send so the writer and the pool never adopt one.

Every measured cost

Machine: Apple M3 Pro, 11 cores, macOS 15, Elixir 1.20.4 on OTP 28, shared with seven other research agents running their own labs, so absolute µs are noisy; ratios are the signal (08).

Two corrections from the review. The spike's 12.7-16.3 µs per Logger.error and 33-40 µs per crash were measured with 12 frames and a 20-crumb ring, and they include inspect and regexes in the failing process, which v1 moves to the buffer (R-13, R-25). Agents read, humans decide

About six of sentry-mcp's ~61 tools matter: search by state, one issue with its recommended event and trail, resolve or mute, a note (report 03). The same Plug serves them, as versioned JSON and as Markdown.

Security rules (ADR section 8)

  • authorize is required: the Plug refuses to mount without it.
  • State-changing routes need a custom x-blackbox header, which a cross-site form cannot send and a cross-origin fetch cannot without a preflight the Plug refuses. No cookie auth.
  • "Localhost only" also checks the Host header, against DNS rebinding.
  • All event text is HTML-escaped; the page sends its own strict CSP.
  • In Markdown, event text sits inside a fence longer than the longest backtick run in it, after a line saying it is data, not instructions.
  • Browser events are an ingest anyone with a board link can write to (/tab/error): they are marked source: browser and untrusted, and left out of the default agent listing. Server-side capture has no ingest at all, and the tracker never starts an agent or runs a fix.

1charta: localhost with a Host check in dev; in prod Basic auth with BLACKBOX_TOKEN for a person, the same token as a Bearer header for an agent. Whether an agent may read prod at all is open question 2.

The PhantomFix lesson (CERT VU#212479, 2026-09-16)A forged error posted to a project's public Sentry DSN fed attacker-controlled messages, stacks and breadcrumbs to Seer, whose coding agent then downloaded and ran an attacker's package before any human review. sentry-mcp marks only Seer's own output as untrusted, not raw event fields. So in Blackbox all event text is fenced as data, the one ingest (browser errors) is marked untrusted and kept out of the default listing, and the tracker never starts an agent or runs a fix.

A quotable id closes the loop: Blackbox.current_ref/0 puts the reference on the error page and in JSON errors ("1charta had trouble. Reference a1b2c3."), so a person or an agent can paste it. Dev issue files (tmp/blackbox/*.md) are later; agents can curl the .md route meanwhile.

No error historyLogs go to stdout only; the container is recreated on every deploy with a 50 MB cap. 168 h of prod logs: 3,683 lines, all [info], 0 errors.
